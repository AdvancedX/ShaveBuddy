# ShaveBuddy 交付路线图

状态：开发前计划  
日期：2026-08-15

## 总体策略

按“先消除移动端未知，再完成最短核心循环，最后补齐可信度”的顺序推进。每个阶段都应产生一个能在 Android 与 iOS 运行的纵向切片，避免先把所有数据库或所有页面一次性写完。

## 阶段 0：技术验证

目标：证明选择的技术栈能可靠承担本项目最关键的平台能力。此阶段代码允许丢弃，不追求正式视觉。

范围：

- 初始化 Expo + TypeScript 项目并锁定依赖；
- 从技术验证开始使用 development build；Expo Go 只用于快速预览，不作为原生通知行为的验收环境；
- 配置三个占位路由；
- 创建一张测试表，执行第一条版本化迁移；
- 写入记录并验证应用重启后仍存在；
- 请求通知权限，调度一条短时本地通知；
- 在 Android 不申请精确闹钟特殊权限的前提下验证可接受的日期提醒；
- 修改数据后取消旧通知并重排；
- 在一台 Android 和一台 iPhone 真机验证；
- 为日期纯函数加入跨日、月底、闰年、夏令时和时区样例。

退出条件：满足《技术方案与架构决策》的全部“决策转正条件”，并把结果追加为 ADR 记录。未满足时先记录证据，再决定修正实现或对 Flutter 做等范围验证。

## 阶段 1：最短核心循环

目标：用户能建立当前装备，记录一次剃须，并看到正确的状态变化。

范围：

- 首次使用流程；
- 装备与耗材周期的正式数据库迁移；
- “今天”页；
- 一键记录与补记；
- 使用次数、使用天数、上次/下次日期计算；
- Repository 与领域规则测试；
- 中文基础文案、浅色/深色主题 token、动态字体基础支持。

退出条件：从全新安装到第一次记录的完整流程能在两端完成；应用重启和跨日后状态正确。

## 阶段 2：历史与更换闭环

目标：让记录可回顾、可纠错，让耗材能完成完整生命周期。

范围：

- 月历与日期详情；
- 编辑、删除记录；
- 更换耗材并查看历史周期；
- 多件装备的数据支持；
- 修改历史后重新计算状态并重排提醒；
- 空状态、错误状态和破坏性操作确认。

退出条件：新增、补记、编辑、删除、更换五类动作之后，首页、日历、装备历史和通知始终一致。

## 阶段 3：提醒、数据可携带与发布质量

目标：让应用在真实设备上长期使用时可信、可恢复。

范围：

- 正式通知引导与设置；
- 下一次剃须和日期阈值提醒；
- 权限拒绝、系统关闭通知后的降级体验；
- 版本化 JSON 导出、校验、导入与恢复；
- 无障碍标签、对比度、动态字体、触控区域检查；
- 性能、崩溃、数据库升级和安装包测试；
- 应用图标、启动画面、隐私说明和商店素材。

退出条件：产品文档中的 MVP 成功标准全部通过，且两端完成发布候选版真机回归。

## 阶段 4：小范围验证

目标：先验证核心循环是否真的值得长期维护，再扩大功能。

建议邀请少量不同类型的剃须用户连续使用 2–4 周，访谈而不是急于增加埋点。重点了解：

- 他们是否真的在剃须后立即记录；
- 记录入口是否足够快；
- 次数和天数哪个更有决策价值；
- 下一次提醒是否有帮助或造成打扰；
- “舒适度”是否值得保留；
- 多件装备的切换是否符合真实习惯；
- 哪些数据会让他们愿意长期保留应用。

验证后才考虑云同步、小组件、耗材库存、统计趋势或商业化。

## 开发前检查清单

- [ ] 确认首发用户与首发语言；
- [ ] 确认手动刀片、卡式刀头、电动刀头的命名；
- [ ] 确认次数/天数默认值只是可编辑建议；
- [ ] 准备 Android 与 iOS 真机测试条件；
- [ ] 完成阶段 0 并记录证据；
- [ ] 技术决策从“暂定采用”转为“正式采用”；
- [ ] 冻结 MVP，不把阶段 4 候选项提前带入开发。

## 首批工作项顺序

技术验证通过后，按以下顺序拆分任务：

1. 领域日期类型与寿命计算规则；
2. 数据库迁移框架和 Repository 接口；
3. 装备/耗材首次设置纵向切片；
4. 一键记录纵向切片；
5. “今天”状态展示；
6. 日历历史与记录纠错；
7. 更换耗材闭环；
8. 通知重排；
9. 导入导出；
10. 无障碍、真机回归与发布准备。
